## §5.16 checklist: findings, evidence, impact

1. **Scenario is in `practice_drafts` before Vault; canonical `practice_tasks` is created only during promotion.** Draft row owns `prompt_chinese`, fixed instructions/goal and future expression ID (`supabase/migrations/202608160011_practice_drafts.sql:5–32`; `src/server/domain/create-practice-task.ts:339–360`). Promotion copies draft to canonical task with same task UUID (`202611010020_learning_card_fields.sql:275–288`). Candidate selection is `(saved_item_id,candidate_artifact_id,candidate_index)` (`create-practice-task.ts:51–61`). **Important group-1 identity rule:** modern cards have `highlightKey`, and deterministic draft identity uses `(owner,saved_item,highlightKey)` across replacement analysis artifacts (`create-practice-task.ts:301–314`); old cards fall back to artifact/index. **Impact:** add round/scenario fields to drafts and copy relevant scenario fields to canonical tasks on promotion; do not mistakenly make a draft create Vault evidence on activation. Persist a stable server-computed candidate identity that retains modern highlight identity across artifact versions; artifact+index alone is insufficient.

2. **Revision already resets per draft, so one-row-per-round makes revision 1 naturally round-local; don't redefine revision as global.** Production TS gates: `src/server/repositories/attempt-repository.ts:214` (promoteIfEligible), `:255` (original submission), `:553` (findOriginalAttempt), `:561–565` (nextRevision scoped by draft). Separate business gate `src/server/domain/record-valid-attempt.ts:59–66`. SQL historical gate `202608160012_promote_practice_attempt.sql:144`; private implementation revision gate `202611010020_learning_card_fields.sql:125` (later 022/023 patch other parts). `practice_draft_attempts` uniqueness is `(practice_draft_id,revision)` (`011:159–168`). **Impact:** keep “revision 1 of owned round” in all these locations, require matching owned draft linkage and candidate-level not-already-promoted fence. Historical migrations are not edited; new migration replaces current private implementation. Do not loosen revision=2 guard just to allow round 2.

3. **Receipts are private, attempt-keyed, immutable; no candidate-level uniqueness currently exists.** Original receipt schema `012:1–55`, primary key `practice_draft_attempt_id`; graph contains draft/task/expression/attempt/mastery/review IDs, deterministic due and normalized expression. `202608220016_source_deletion.sql:10–34` changes receipt FKs to canonical attempt/task and preserves deleted occurrence identity. Public RPC is a source-deletion-compatible exact replay wrapper (`016:51–125`) calling `private.promote_valid_practice_draft_attempt_source_active`; group 1 replaces private body (`020:36–362`), then **022:54–72 dynamically patches public/private length guards to 10000 and 023:5–24 dynamically patches private modern-card confidence compatibility**. **Impact:** build from effective function definition or compose 020+022+023; copying 020 verbatim would regress long expressions and confidence-free modern learning cards. Also preserve wrapper, after-source-deletion replay and private grants. Add durable candidate key to promotion guard/receipt (owner + stable candidate key unique); candidate-level lock must serialize all rounds and both activation/promotion so two eligible rounds cannot create two Vault graphs. Receipt existence query must be a service-only RPC or within definer functions, because service_role cannot SELECT private receipts (`012:50–52`; SQL test `promote_practice_attempt.sql:554–562`). Don't expose private table with broad grants merely to implement POST-task redirect.

4. **Prompt identifiers follow strings, not file suffixes.** `activate.v1.ts:15–22` exports current `activate-practice-v2` and readable v1/v2. `evaluate.v1.ts:51–60` exports `evaluate-practice-v4` and readable v1–v4. New files should be `activate.v2.ts` => version v3, `evaluate.v2.ts` => version v5; leave old builders usable. `PracticeCoachingSchema` requires a string inside object (`src/contracts/practice.ts:79–86`), while the *object* is nullable. Wire `naturalRevisionChinese` is already optional (`evaluate.v1.ts:73–78`), invalid/missing/non-target revision yields coaching null (`:193–202`). **Impact:** don't force `naturalRevisionChinese:null` through current string schema. For all-5 ignore any model rewrite and return/store coaching null. New metadata-complete tasks use v5, missing new fields keep v4 (§8.5). Store coaching for round refresh: currently insertAttempt persists no coaching and recovered original always returns `coaching:null` (`attempt-repository.ts:195–198`, `:229–237`, `:568–592`). Add nullable natural revision persistence to draft-attempt rows, including revisions; not reconstruct with another model call.

5. **Local demo backfill read-only projection verified; migration execution not yet verified.** Used read-only PostgreSQL transactions, no row text or IDs printed. Local migrations include through `202611010023`; draft counts active=4/completed=7; original attempts=8, receipts joined to live drafts=7; abandoned=0; duplicate `(owner,saved,artifact,index)` groups=0; one draft has modern highlightKey. ## Shared contracts to freeze before delegating implementation

Suggested signatures (names may vary; behavior is authority):

```ts
type PracticeRoundStatus = 'open'|'retry_scheduled'|'promoted'|'superseded'|'removed';
type RoundAnswer = { attemptId:string; revision:number; text:string; evaluation:EvaluationResult; naturalVersion:string|null };
type PracticeRoundState = {
  roundNumber:number; status:PracticeRoundStatus;
  firstAnswer:RoundAnswer|null; latestRevision:RoundAnswer|null;
  examplesOpened:boolean;
  promotion:{userExpressionId:string;nextDueAt:string}|null;
  retryDueAt:string|null;
};
type ActivatePracticeResult = PracticeTask | {redirect:string};
type StartRoundResult = {taskId:string;roundNumber:number;created:boolean};
type RemoveResult = {roundState:PracticeRoundState;undoUntil:string};
activate(userId:string, selection:CandidateSelection):Promise<ActivatePracticeResult>;
startRound(userId:string, taskId:string, requestId:string):Promise<StartRoundResult>;
remove(userId:string, taskId:string):Promise<RemoveResult>;
restore(userId:string, taskId:string):Promise<{roundState:PracticeRoundState}>;
openExamples(userId:string, taskId:string):Promise<{examplesOpened:true}>;
openDueExamples(userId:string, reviewTaskId:string):Promise<{examplesOpened:true}>;
getRoundState(userId:string, taskId:string):Promise<PracticeRoundState|null>;
submitOriginal(userId:string, {taskId,responseChinese}):Promise<PracticeAttemptResponse /* includes roundState */>;
submitRevision(userId:string, attemptId:string, responseChinese:string):Promise<PracticeAttemptResponse /* includes roundState */>;
resolvePracticeReturnTo(input:unknown):{href:string;label:'Saved'|"Today's practice"|'Vault'|'Home'};
```

- Preserve existing outer `success()` envelope. Add typed discriminated payload for 409 FIRST_ANSWER_EXISTS with full existing answer/roundState, 409 ALREADY_PROMOTED with userExpressionId. Rounds returns 201 created; 200 current open/replay according to frozen receipt semantics. Other mutation response statuses should be explicit contract tests.
- Prompt-facing enriched scenario: `{situationZh,situationEn,interlocutor,taskEn,targetFunction,targetSetting}` stored with activation version and fingerprint; keep legacy `promptChinese` mapping for old callers. Scoring union: complete enriched metadata => v5; old shape => v4. Don't invent new targetMeaning for old tasks from unrelated text.
- Stable candidate key recommended: server-only `highlight:<savedItemId>:<highlightKey>` for modern; `legacy:<savedItemId>:<artifactId>:<index>` otherwise. Persist in draft and immutable receipt. Candidate locking/uniqueness includes owner. Backfill source-deleted legacy receipts without source FK requirement. Choice of helper/RPC versus table is engineering; no need for product confirmation if semantics remain stable.
- Fingerprint spec demands different previous situation, not just different task ID. Avoid reusing canonical due fingerprint (hash expression+prompt+instructions+goal in `014:10–29`), which changing taskEn could satisfy while situation repeats. Define one normalized-situation hash shared TS/SQL for new first-practice rounds and compare all prior rounds; do not alter existing mastery-context fingerprint or owned thresholds.
- Need freeze race responses: superseded task submit, remove vs round creation, restore vs newer round, examples vs answer, two distinct round requestIds; safe response cannot create a branch, resurrect a stale draft, promote twice, or reset original retry date. These are contract-level engineering cases, not authority for changing user flow.
