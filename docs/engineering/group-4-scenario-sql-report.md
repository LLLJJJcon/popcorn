## Exercised lifecycle behavior

- Initial preparation has one claimed winner; another request UUID becomes a waiting alias, and exactly one active claim exists. The alias observes ready after the winner publishes. Repeated ready recovery makes no persisted task or operation change. This is SQL state evidence, **not a claim about observed model-call counts**.
- Request-signature changes under the same ID are rejected. A successful regeneration replays with its original request ID and original version/hash, both before and after official completion. A fresh request with an old identity still fails `SCENARIO_CHANGED`; a fresh second regeneration with current identity fails `REGENERATE_USED`.
- A distinct regeneration waiter keeps its own request ID while pending, but cannot borrow the winner's success: its lookup and claim receive `REGENERATE_USED`, or `ALREADY_SUBMITTED` after official completion. The original winner still replays successfully, and ordinary initial-preparation aliases still share their winner.
- Failed waiters retain their original failed cycle instead of creating a new claim or silently joining a later fresh retry. Expired-winner waiters also remain failed under their own ID and create zero live claims. Repeating a successful winner's publication returns its exact task receipt, leaving task, archive and operation rows unchanged.
- Initial publication stores version 1 and one snapshot. Only successful regeneration increments to version 2 and consumes the allowance. Old and new snapshots are persisted exactly once; the original snapshot retains its original mastery-context fingerprint. Regeneration keeps the actual near/far direction.
- A candidate differing only in punctuation/whitespace from a prior situation fails `SCENARIO_DUPLICATE`. A failed regeneration records its failed cycle while preserving the complete prior question row, scenario/mastery hashes, version, markers and allowance. Same failed ID remains failed; a new explicit retry can succeed.
- Reveal persists without examples assistance. Examples preserves the first reveal timestamp, and when used first atomically persists both markers. Successful replacement inherits those durable review markers. Stale marker identity is rejected.
- Wrong owner cannot claim, publish with a stolen token, mark, look up an outcome or fail another owner's cycle. All five lifecycle RPCs have service-only execute access; actual authenticated/anonymous calls are denied, and private operation tokens/receipts are inaccessible to browsers.
- Wrong or expired claim tokens cannot publish. An expired cycle cannot falsely confirm a failure write; read-only lookup reports its failure and a fresh request can reap it, leaving one live claim. The old token remains fenced.
- A valid owned task appearing after an initial expected-version-zero claim makes that claim stale; publication fails `SCENARIO_CHANGED` instead of overwriting the newer task.
- Worker fences enforce job ownership, exact attempt count, exact lease timestamp and nonexpired lease. Publication rechecks a changed worker attempt after model work and leaves no partial task; a fresh valid worker cycle publishes once.
- The job-fence fixture uses an existing supported leased `analyze_saved_item` row only to exercise 033's generic job owner/attempt/lease checks. It does **not** claim acceptance of the separate `prepare_transfer_task` outbox/job-kind integration.
- A real official completion wins over a previously claimed replacement; later publication fails `ALREADY_SUBMITTED`. Fresh replacement after completion is rejected. Already successful same-ID recovery remains a safe ready replay.
- Before intentional official completions, complete stored rows for official attempts, mastery events, user-expression state and review schedules compare unchanged after preparation, replacement and marker operations (excluding the two intentionally written disclosure fields).

The SQL file stages interleavings deterministically inside one rollback transaction. Independent real-connection concurrency and full job/runtime integration remain D/A acceptance work.
